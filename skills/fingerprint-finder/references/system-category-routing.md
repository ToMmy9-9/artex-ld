# 按系统分类的编排路由（A/B/C/D/E）

> 本文件是 fingerprint-finder 给出 **A/B/C/D/E 判定结果**后的可执行编排模板。
>
> 判定规则（什么算 A/B/C/D/E）见 [system-categories.md §2](system-categories.md#2-系统形态--测试策略映射abcde-判定)。
> memory-search-mcp 在每个阶段按特征动态触发，不由本文件步骤顺序决定。

---

## 通用前置流程（所有类别）

```
skill('pentest-workflow')（主编排器，7 类智能场景调度）
  ↓
skill('fingerprint-finder')（指纹 + 认证结构识别 + 系统分类判定 A/B/C/D/E）
  ↑ memory-search-mcp 在此阶段根据识别的技术栈/行业动态加载
  ↓
【分类检查点】→ 按 A/B/C/D/E 分支到对应编排（见下方）
```

fingerprint-finder 判定证据不足时，统一按 **B 类**（双线并行）保守处理，避免激进跳过业务逻辑。

---

> ⚠️ **A类编排前提**：A类=第三方商业产品（用友/致远/泛微/Jenkins/Nacos等），不是"有CVE的自研系统"。**系统建设方自研系统即使有CVE也走B/C类**，严禁把自研系统错误路由到A类POC主路径。

## A 类（成熟商业产品）编排

```
分类判定 A 类
  ↓
【POC 主路径 - 立即触发】skill('poc-scan') ⭐
   ├─ 本地 POC 库穷尽（rg 检索语料，命中 POC 全部执行）
   ├─ 互联网搜索（WebSearch / query_cve 多源）
   ├─ POC 变种尝试（路径变形 / WAF 适配 / 利用链上下文）
   └─ 嵌入组件深度探测（Actuator / 子系统完整版本 / 第三方组件 nday）
  ↑ memory-search-mcp 在此阶段加载 POC 维度经验
  ↓
【轻量业务逻辑兜底】（≤30 分钟，避免漏报）
  ├─ 用户列表 / 数据导出 / 密码重置 / 支付 / 管理后台
  └─ 发现漏洞则深入，否则跳过
  ↓
skill('api-tester')（仅凭据获取环节）+ skill('sensitive-info-leak')（全程伴随）
  ↑ memory-search-mcp 在此阶段根据漏洞模式动态加载
  ↓
报告生成
```

## B 类（自研含组件）编排

```
分类判定 B 类
  ↓
【双线并行启动】
  ├─ 业务逻辑线：skill('api-tester')（接口发现 + 自研认证矩阵 a-i）
  └─ POC 库线：skill('poc-scan') ⭐（仅嵌入组件识别后触发）
  ↑ memory-search-mcp 同步加载
  ↓
skill('sqli-tester')（数据库接口时触发）+ skill('sensitive-info-leak')（全程伴随）
  ↓
skill('api-tester')（越权 + 逻辑漏洞测试）+ skill('sensitive-info-leak')（全程伴随）
  ↓
【中期重新评估检查点】（POC 耗尽 + 业务逻辑均 0 命中才触发）
  ↓
skill('response-modifier')（响应篡改）+ skill('sensitive-info-leak')（全程伴随）
  ↓
报告生成
```

  ↓

## E 类（混合架构）编排

按主导部分归类，附属部分按对应类别编排轻量执行（≤30 分钟）：

| 主导部分 | 归类 | 附属部分处理 |
|---|---|---|
| 核心业务是商业产品 | A 类 | 自研扩展轻量测试 |
| 核心业务是自研 | B 类 | 商业组件嵌入轻量测试 |
| 自研业务 + 嵌入开源组件 | B 类或 D 类 | 按是否含组件判定 |
| 商业产品 + 自研扩展 | A 类 | 自研部分轻量测试 |

判定细节见 [system-categories.md §2.3](system-categories.md#23-e-类混合架构识别信号)。

---

## 关键约束

- **A/C 类：poc-scan 作为第一步立即触发**（POC 主路径原则），不再先走 api-tester
- **B 类：双线并行**（业务逻辑 + POC 同步）
- **D 类：api-tester 全流程**（业务逻辑主路径）
- **中期评估**：所有类别都必须等"对应主路径资源耗尽"才触发，不因几次失败就切换
- **轻量业务逻辑兜底**：即使 A 类也必须执行用户列表 / 数据导出 / 密码重置 / 支付 / 管理后台五项

---

## 中期重新评估机制

**前置条件**（必须全部满足）：
- 本地 POC 库穷尽（rg 检索语料 + 全部命中 POC 执行完毕）
- 互联网搜索完成（WebSearch / query_cve / cnblogs / xz.aliyun 等多源）
- POC 变种尝试完成（路径变形 / WAF 适配 / 利用链上下文 / Host 头伪造）
- 嵌入组件深度探测完成（Actuator 全部端点 / 子系统完整版本清单）

**触发条件**（前置条件全部满足 + 任一）：
- POC 验证 0 命中（不是 ≥5 失败，是 0 命中）
- 未授权端点探测 0 命中
- 嵌入组件版本过新（最新版本无公开 CVE）
- 总测试时间超过预算 50% 仍 0 命中

**重新评估动作**：补充业务逻辑测试 / 重新审查指纹证据 / 必要时切换分类

**⚠️ 关键原则**：不要因为"几次 POC 失败"就放弃 POC 路径，必须等所有 POC 资源耗尽才评估。

## 场景映射规则

> 本文件是 fingerprint-finder 输出 A/B/C/D/E 分类后的**场景级编排指引**。
> fingerprint-finder 断言分类后，同时输出推荐场景编号，本规则定义了分类 → 场景的映射逻辑。

### 核心映射逻辑

```
fingerprint-finder 输出：
  test_strategy: A / B / C / D / E
  recommended_scenario: 1-7
  scenario_reason: "映射理由"
  product_name: "用友 NC / Jenkins / 未知"  # 已知产品名
    ↓
pentest-workflow 场景二次确认：
  ① 检查初始场景编号（用户输入匹配）
  ② 对比 fingerprint-finder 推荐的场景编号
  ③ 不一致 → 按以下规则决定是否重定向
```

### 分类 → 场景映射表

| 分类 | fingerprint 输出信号 | 推荐场景 | 重定向规则 |
|------|-------------------|---------|-----------|
| **A 类** | product_name 为已知商业 OA（用友/致远/泛微） | 场景 6 | 强制重定向（即使输入是场景 1）；⚠️ 自研系统有CVE记录 ≠ A类 |
| **A 类** | product_name 为独立中间件/运维工具（Jenkins/Nacos/1panel） | 场景 1 | 保持场景 1，走 POC 主路径 + 中间件专项子路径 |
| **A 类** | product_name 未知（通用商业产品，但无法确定具体产品名） | 场景 1 | 保持场景 1，走 POC 主路径 |
| **B 类** | 自研 + 嵌入组件（Spring Boot/Shiro/Fastjson 等） | 场景 1 | 保持场景 1，双线并行 |
| **C 类** | 开源二开（JeecgBoot/若依/Metabase 改造） | 场景 1 | 保持场景 1，POC 主路径 + 二开业务逻辑 |
| **D 类** | 纯自研无组件 | 场景 4（优先）→ 场景 1（回退） | 初始场景若非场景 4 → 检查是否应切换到场景 4 |
| **E 类** | 混合架构，主导部分为 A 类 | 场景 6 或场景 1 | 按主导部分规则 |
| **E 类** | 混合架构，主导部分为 B 类 | 场景 1 | 保持场景 1 |
| **无法判定** | 证据不足 | 场景 1 | 回退场景 1，B 类保守处理 |

### 指纹信号 → 场景重定向矩阵

| 指纹信号 | 初始场景 1 | 初始场景 2 | 初始场景 3 | 初始场景 4 | 初始场景 5 | 初始场景 6 | 初始场景 7 |
|---------|-----------|-----------|-----------|-----------|-----------|-----------|-----------|
| 商业 OA 产品名 | → 重定向到场景 6 | → 重定向到场景 6 | 保持 | 保持 | → 重定向到场景 6 | 保持 | 保持 |
| 独立中间件 | 保持 | 保持 | 保持 | 保持 | 保持 | 保持 | 保持 |
| 纯自研 D 类 | 保持 | 保持 | 保持 | 保持 | 保持 | 保持 | 保持 |
| 自研含组件 B 类 | 保持 | 保持 | 保持 | 保持 | 保持 | 保持 | 保持 |
| 无法判定 | 保持 | 保持 | 保持 | 保持 | 保持 | 保持 | 保持 |

> **重定向原则**：只有"当前场景明显不合适"时才重定向，避免频繁切换打断测试流程。
> 例如：场景 4（API 安全测试）中识别出商业 OA 产品 → 不强制重定向，因为 API 测试也是 OA 测试的一部分。

## 子目标发现与路由

> 测试过程中，api-tester / sensitive-info-leak 等 skill 可能发现与主目标技术栈完全不同的新入口（如前端 JS 中挖出 `/admin/login` 指向独立的 Spring Boot 后端系统）。

### 触发条件

```
api-tester 接口发现 / sensitive-info-leak JS 分析
  ↓
发现新入口（如 /#/admin → 加载新 JS bundle、/manage/ → 不同响应头、/api2/ → 不同技术栈）
  ↓
【子目标发现检查点】→ 判断是否属于独立子系统：
  │
  ├─ 同系统（同技术栈 / 同前端框架 / 同 API 风格）
  │  └─ 不触发，当前流程继续
  │
  └─ 新子系统（满足 ≥2 项）：
      ├─ 不同技术栈（如 Vue → React、前端 → Spring Boot 后端）
      ├─ 不同响应头（如 X-Powered-By: Express → ASP.NET）
      ├─ 不同域名/路径前缀（如 /api/v1 → /backend/）
      ├─ 独立认证入口（如独立的登录页 / SSO 端点）
      └─ 不同静态资源目录（完全不同的前端 JS bundle）
        ↓
        skill('fingerprint-finder') 对新入口重扫
          ↳ 限定范围：只扫新发现路径，不重扫全量
          ↳ 获得新系统的 A/B/C/D/E 分类
        ↓
        【分类判定】→ 新系统与主目标的关系：
          │
          ├─ 同分类（如都是 B 类）→ 合并到主目标测试流程，补充测试范围
          │
          └─ 不同分类（如主目标 A 类、新入口 D 类）→ 作为子目标独立编排
              └─ 启动子目标测试流程（按新分类走对应编排）
              └─ 并行或串行执行（视资源情况）
              └─ 报告合并：主目标 + 子目标统一输出
```

### 主目标与子目标的关系

| 维度 | 主目标 | 子目标 |
|---|---|---|
| 触发源 | 用户输入 | 测试过程中发现 |
| 分类判定 | 初始 fingerprint-finder 完成 | 发现后即时判定 |
| 编排路径 | 按 A/B/C/D/E 完整编排 | 按新分类独立编排 |
| 测试范围 | 全量 | 限新发现的路径 + 关联组件 |
| 报告输出 | 合并到最终报告 | 作为子章节附加 |

### 关键约束

- **轻量触发**：子目标检查点不阻塞主流程，发现新入口后立即判定，判定后异步启动子目标
- **范围限定**：子目标只测新发现路径及其关联组件，不做全量重新探测
- **分类变更**：若子目标分类与主目标不同，不影响主目标当前编排，两者独立执行
- **资源控制**：子目标使用的并发资源不超过主目标的 30%，避免主目标测试被拖慢
- **深度限制**：子目标不再递归发现子目标（防止无限嵌套）
