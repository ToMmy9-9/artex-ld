# 接口越权测试（api-authz）

## 适用场景

目标是带登录体系的 Web / App / API 时，越权（横向越权 BOLA、纵向越权 BFLA）通常是**命中率最高、最容易被接收**的一类漏洞。
本技能给的是一条可复现的三段流程：**拿接口清单 → 双身份请求 → 差异判定**。不要跳过任何一段直接"猜参数"。

## 前置：三种身份，缺一不可

| 身份 | 来源 | 用途 |
| --- | --- | --- |
| **匿名**（无凭据） | 直接请求，不带 Authorization / Cookie | 判「未授权访问」——最高危，最容易证明 |
| **低权 A** | 普通用户会话（自己注册或已提供的测试账号） | 横向越权的基线所有者 |
| **低权 B** | 另一个普通用户会话（**必须与 A 不同主体**） | 用 B 的凭据访问 A 的资源 |

> 只有 A 没有 B 时，仍可测匿名可达性与 BFLA（低权访问管理员接口）；但**横向越权必须有两个不同主体的账号**，否则结论只能写 inferred。

## 第一段：拿接口清单

优先复用平台已有的情报，不要从零爆破：

1. `list_assets(type=endpoint)` / `asset_neighbors` —— 已探到的端点与它们所属的服务。
2. `traffic_search(body_contains=...)` —— 已录制流量里出现过的 API 路径，命中率高且自带真实请求头。
3. 前端 JS / 路由表：`api-recon` 技能里的静态抽取脚本可从 bundle 恢复路由与参数。
4. 只在前三步覆盖不足时才做目录探测，且**降速、限并发、限字典**，并在证据里写明探测范围。

产出必须是一张**接口表**：`method + path + 鉴权方式 + 参数 + 所属对象类型`。
对象类型是越权测试的核心：`order`、`user`、`file`、`invoice`……决定用什么 id 去替换。

## 第二段：双身份请求

对接口表里每一条，按固定矩阵发请求：

```text
匿名  →  期望 401/403；若 200 且含业务数据 = 未授权访问
A 访问 A 的资源  →  200（基线）
A 访问 B 的资源  →  若 200 且响应含 B 的数据 = 横向越权（BOLA）
B 访问 A 的资源  →  反向确认，排除"服务端按最新登录用户返回"的假象
低权 A 访问管理接口  →  若 200 = 纵向越权（BFLA）
```

要点：

- **一次只改一个变量**。同一请求、同一 Host、同一时间窗口，只换凭据或只换对象 id。
- **对象 id 只换可预测位**：自增数字、短 UUID、base64 编码的 `userId:123`、`tenantId` 前缀。不要遍历全量，取 3–5 个相邻值即可证明可越权。
- **参数位置都要试**：`path` / `query` / `body` / `header`（`X-User-Id`、`X-Tenant-Id`、`X-Org-Id` 这类常见越权向量）。
- **写接口单独成一类**：`PUT/PATCH/DELETE` 的越权比读更严重，但风险也高——先只对**自己创建的测试对象**做写操作，绝不动他人真实数据。
- 所有请求必须走录制代理（`:8788`），事后才能绑定真实报文作为证据。

## 第三段：差异判定（这一步决定结论真伪）

只看状态码会误判。按下面顺序判：

| 观察 | 结论 |
| --- | --- |
| 200 + 响应体含**他人**业务字段（姓名/手机/金额/地址/订单号） | 确认越权（observed） |
| 200 但响应体是空对象 / 全 null / 通用占位 | 不足以判定，继续换 id 或字段 |
| 200 + 返回的是**当前登录用户自己**的数据 | 不是越权（服务端做了身份绑定） |
| 403 / 401 / 302 → 登录页 | 无越权，记录为否定结论 |
| 200 + WAF 拦截页 / 跳转 / 验证码 | **目标侧防御**，不是越权结论，也不是平台拦截 |

**关键判据**：把 A 看到的响应、B 看到的响应、匿名看到的响应三者**并排比对字段值**。
只有"用 B 的凭据拿到了 A 的字段值"才算横向越权；只说"都能访问"不算。

## 误报排除清单

提交前逐条过一遍，任一条命中就不要报：

- [ ] 响应里的数据是不是**请求者本人**的？（最常见误报）
- [ ] 是否只是**接口存在**（200 + `{"code":0}`），没有真实业务数据？
- [ ] 是否命中了 **WAF 的 200 拦截页**（页面含 WAF 特征、无业务字段）？
- [ ] id 换成不存在的值是否也返回 200？（说明服务端不校验存在性，不能证明越权）
- [ ] 是否**两个账号其实是同一个主体**（同一 cookie、同一 userId）？
- [ ] 是否只是**前端隐藏了入口**，后端本来就没鉴权要求（如公开列表接口）？

## 证据要求

每条确认的越权必须能机械复现：

1. **两个身份**：A 的账号标识、B 的账号标识（脱敏后可写入报告）。
2. **两条真实请求**：`curl` 或原始 HTTP，含完整路径、鉴权头（脱敏）、对象 id。
3. **两条真实响应**：状态码 + 关键字段（他人才有的字段必须原样保留）。
4. **对比说明**：一句话说清"用谁的凭据、访问了谁的资源、拿到了什么"。
5. 绑定 `traffic_id`（真实报文），report_finding 时附 `reproduction` 的分步过程。

## 与其他技能的关系

- 只测对象 id 可预测性 → `idor-testing`（本技能的超集，含更多编码变体）。
- 需要先摸清接口与指纹 → `api-recon` / `fingerprint-finder`。
- 需要判断鉴权绕过（401/403 绕过、路径大小写、双写头） → `route-guard-bypass`。
- 需要批量对比参数/响应差异 → `api-tester`。
