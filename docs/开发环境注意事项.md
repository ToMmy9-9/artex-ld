# 本机开发环境注意事项

记录在当前这台 Windows 开发机上实测到的环境坑，避免后来者重复踩。

## 零、怎么把系统跑起来（前后端 + 数据库）

整体分两部分：**Go 后端（:8787）** 和 **Next.js 前端（:3000）**。开发时前端把 `/api/*`
反代到后端，所以两个都要起。

### 1. 后端

```bash
export ARTEX_PG_DSN="postgres://artex:01EDTUB7HLyFQ3ii@127.0.0.1:5432/artex_audit"
cd <repo>
go build -p 4 -o /d/Temp/artex.exe ./cmd/artex   # 记得用干净的 GOCACHE，见第二节
/d/Temp/artex.exe
```

启动成功日志尾部应该是：

```
artex dev backend listening on :8787 (data=data, workers=3)
```

关键点：

- 端口是 **8787**，不是 8080
- 仓库里**没有 `config.json`**，所以必须用 `ARTEX_PG_DSN` 环境变量给数据库连接串，
  否则只会尝试环境变量、失败即退出
- 启动时会打印 `pgvector 不可用…降级为关键词检索`，这是**正常现象**（本机没装
  `vector` 扩展），不影响使用
- `reloaded N task(s) from PG` 表示历史任务已从库里恢复

### 2. 前端

```bash
cd web
npm run dev            # 默认 3000，会把 /api/* 反代到 localhost:8787
```

`next.config.mjs` 里的反代默认目标是 `http://localhost:8787`，可用
`AUTOPENTEST_API` 覆盖。启动后 `Ready in ~1s`，访问 `http://localhost:3000`
会自动 307 跳到 `/login`。

登录：`ARTEX` / `Artex@2026!`（需勾选「使用须知」复选框，登录按钮才出现）。

### 3. 单二进制（内嵌前端）发布形态

默认 `go build` 是 **no-embed** 的，前端 handler 是个 404 桩
（`server/webui_stub.go`），所以根路径 `/` 返回 404 是**预期行为**，不是 bug。
要打出单文件版本：

```bash
cd web && npm run build:static     # NEXT_EXPORT=1 next build，产物在 web/out
cp -r web/out ../server/webui/dist
cd .. && go build -tags embedui ./cmd/artex
```

### 4. 在这台机器上让进程常驻（重要）

**Bash / PowerShell 工具调用里起的进程活不过工具调用边界**。
`nohup ... &` 和 `Start-Process` 都试过：日志显示监听成功，但工具一返回进程就被回收。
要让服务真正常驻，必须用**计划任务**：

```powershell
# 1) 写一个启动脚本（避免 -EncodedCommand，会被安全策略拦）
#    .run.ps1 内容：
#      $env:ARTEX_PG_DSN = "postgres://..."
#      Set-Location "<repo>"
#      & "D:\Temp\artex.exe" *>> "D:\Temp\artex.log"

# 2) 注册并运行
$script = "<repo>\.run.ps1"
$action = New-ScheduledTaskAction -Execute "powershell.exe" `
  -Argument "-NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File `"$script`""
$trig = New-ScheduledTaskTrigger -Once -At (Get-Date).AddSeconds(3)
$set  = New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries `
  -ExecutionTimeLimit (New-TimeSpan -Hours 0) -StartWhenAvailable
Register-ScheduledTask -TaskName "ArtexRun" -Action $action -Trigger $trig -Settings $set -Force
Start-ScheduledTask -TaskName "ArtexRun"
```

两个坑：

- `-EncodedCommand` 会被拦（提示 *Encoded commands hide the actual code being executed*），
  必须写成脚本文件再 `-File` 调用
- `Start-Process` 若环境里同时存在 `HTTPS_PROXY` 和 `https_proxy`，会报
  `字典中的关键字"HTTPS_PROXY"所添加的关键字"https_proxy"` 而启动失败，
  先 `Remove-Item Env:https_proxy` 清掉

前端同理，只是把脚本内容换成 `node <web>/node_modules/next/dist/bin/next dev --port 3000`，
并且**用 node 绝对路径**（计划任务的 PATH 和交互终端不一样，找不到 `npm`）。
用 WorkBuddy 自带 node 时要指到
`C:\Users\1\.workbuddy\binaries\node\versions\22.22.2-6\node.exe`。

停止：`Stop-ScheduledTask -TaskName "ArtexRun"` + `Stop-Process -Name artex-v5 -Force`。

## 一、跑 Go 测试一律加 `-vet=off`（照做即可，理由见下）

**现象**：`go test ./xxx/` 看起来像"编译卡死"——几分钟没有任何输出，进程 CPU 接近 0，
也不派生子进程。

**对照数据**（`reportx` 包，同一份代码、同一个 GOCACHE）：

| 命令 | 耗时 |
|---|---|
| `go build ./reportx/`（热缓存，不链接） | **3.3 秒** |
| `go test ./reportx/ -vet=off` | **0.061 秒，全绿** |
| `go test ./reportx/`（默认带 vet） | 8 分钟超时未完成 |
| `go vet ./reportx/`（单独执行，不链接） | 2 分钟无输出、卡死 |

**归因**：上表是在 `GOCACHE=D:\GoCache2`（已损坏，见第二节）的前提下测的，所以「差多少」
这个数字本身不可靠。但 `-vet=off` 能稳定跑通、默认带 vet 会白等，这个**工程结论依然成立**：
vet 会额外触发一轮完整的包加载与类型检查，在损坏缓存上等于再卡一次。

第二条建议（第二节「换成干净 GOCACHE」）优先级更高。缓存修好后，vet 慢的问题
大概率一并消失；但在确认缓存健康之前，`-vet=off` 仍然是最省事的选择。

```bash
# 一律这样跑
go test ./reportx/ -count=1 -vet=off
go test ./db/ -count=1 -vet=off
ARTEX_PG_DSN="postgres://..." go test ./server/ -count=1 -vet=off
```

不加 `-vet=off` 会白等数小时。想单独做静态检查时，请换一台机器或等 `go vet`
问题查清后再跑。

## 二、`go build` 卡死几十分钟：根因是 GOCACHE 目录损坏（已定位、已闭环）

> **本节曾三度写错，先说明**：初版断言「`D:\GoCache` 目录项 stat 退化到 116ms」，属未经
> 验证的推断；二版把 `timeout 120` 的**超时上限**当成实测耗时写成「hello-world 链接 120 秒」，
> 属伪造数据；三版把矛头指向「整机元数据操作慢 / IDE 争抢 CPU / 沙箱进程占满 CPU」，
> 全部是错误归因。**真正的根因是 `D:\GoCache2` 这个缓存目录本身已损坏**，下面是对照实验。

### 决定性对照实验（可复现）

同一份代码（3 行 hello-world，零依赖）、同一个 Go 二进制
（`C:\Program Files\Go\bin\go.exe`，1.26.1）、同一块磁盘，**唯一变量是 `GOCACHE`**：

| GOCACHE | 第 1 次 | 第 2 次 | 结论 |
|---|---|---|---|
| `D:\Temp\freshcache`（全新空目录） | **1.68 秒** ✅ | **1.60 秒** ✅ | 正常 |
| `D:\GoCache2`（疑似损坏） | 80 秒超时 ❌ | 92 秒超时 ❌ | **永久卡死** |

```bash
cd /d/Temp/hw2   # module hw2 / go 1.26.1 / hello-world
export GOTOOLCHAIN=local GOFLAGS=
for c in /d/Temp/freshcache /d/GoCache2; do
  for i in 1 2; do
    GOCACHE=$c timeout 80 go build -o /d/Temp/x_$i.exe .
  done
done
```

换成干净缓存后，同一个 48MB 的 `artex` 主程序 **46 秒编译完成**（`go build -p 4 ./cmd/artex`）。
在此之前，这个命令在本机已经连续失败过十几次、累计耗掉数小时。

### 修复方法

**不要试图修 `D:\GoCache2`。换一个新的空目录即可。**

```bash
# 建一个新的干净缓存目录（放在空间充裕的盘）
mkdir -p D:/GoCache-new

# 之后一律这样用
export GOCACHE=D:/GoCache-new
go build ./cmd/artex
```

想在 shell 里永久生效，设置用户环境变量 `GOCACHE=D:\GoCache-new`，然后重开终端。
损坏的旧目录可以直接删掉（注意：在 WorkBuddy 沙箱内批量删除可能触发
`safe-delete` 守卫，建议用资源管理器或 `Remove-Item` 在沙箱外删）。

### 卡死时的典型特征（用于快速识别）

- `go build -x` **只打印 `WORK=D:\Temp\go-buildXXXX` 一行就再无输出**，说明它卡在
  启动第一个编译子进程之前
- 进程 CPU 时间接近 0，且**不派生** `compile.exe` / `link.exe` 子进程 —— 在等待，不是在计算
- 已经全部缓存的包（第二次编译同一份代码）**同样卡死**，这一点最关键：
  正常缓存命中应该是毫秒级，不可能卡住
- `go env XXX` 一直正常（**150~250ms**），`go list -f '{{.Name}}' .` 也可能只要几秒 ——
  所以「go 本体坏了」的判断是错的，坏的只是缓存读写路径

### 排除掉的（都不成立，别再往这些方向查）

| 曾经的怀疑 | 实测 | 结论 |
|---|---|---|
| 整机文件系统元数据退化 | 写 2000 文件 2.1s、stat 2000 次 81ms、单次 stat 0.046ms | **正常** |
| `D:\Temp` 条目过多（3.4 万个） | `listdir` 34464 条目仅 **10.5ms** | **正常** |
| GOROOT 源文件读取慢 | 读 7701 个 `.go` 文件共 90MB 仅 **6.82s** | **正常** |
| 编译器/链接器二进制损坏 | `compile.exe -V` 143ms、`link.exe -V` 1107ms、真实编译 151ms | **正常** |
| toolchain 转发死锁 | 直接用 1.26.10 工具链同样卡死 | 转发机制无罪 |
| CPU 被 IDE / 沙箱占满 | 整机 CPU 降到 17% 时仍卡死；`sandbox-center` 重启后仍卡死 | 与 CPU 争抢无关 |
| 提交内存不足 | 权威口径 `\Memory\Commit Limit` 22.36/39.10 GB（57%） | **正常** |
| `.exe` 扩展名触发杀软扫描 | 复制为 `.exe` 与 `.dat` 耗时均约 4.9 秒 | 无差异 |
| 仓库/依赖问题 | 全新 3 行 hello-world 同样卡死 | 与仓库无关 |

**曾一度被误认为根因的**：`sandbox-center.exe` 占 99% CPU（累计 2115 秒）。重启后 CPU
归零，`go list` 从卡死恢复为 23.6 秒可完成，但 `go build` **依然卡死** —— 所以它是
这台机器变慢的**并发症状**，不是 `go build` 卡死的原因。

### 一个容易踩的附带坑：沙箱的 safe-delete 守卫

WorkBuddy 沙箱对删除操作有 `safe-delete-bulk-guard` 检查，偶尔会报：

```
[safe-delete][SAFE_DELETE_BULK_GUARD_ERROR] state lock timeout
[safe-delete][SAFE_DELETE_BULK_GUARD_ERROR] ... timed out after 10 seconds
```

这会让 `rm -f` / `Remove-Item` 偶发失败（同一个删除命令重试往往就过了）。
实测三个目录（`D:\GoCache2`、`D:\Temp\freshcache`、`D:\Temp`）删除单个文件的耗时
都在 **1 秒左右**，无目录差异，所以它是偶发的守卫锁问题，**与 go 编译卡死无关**。

需要在大量文件上做删除时，改用 PowerShell `Remove-Item -Force` 或直接在
资源管理器里删，别用 shell 的 `rm`。

### 关于缓存 key 的一个正常现象

Go 的缓存 key 包含源码**绝对路径**，所以同一个包在不同目录下编译不会互相命中。
在 C 盘仓库和 D 盘迁移副本之间切换时，第一次编译都要重新建缓存，之后才会快。
这不是问题。


## 二之二、跑大包测试别用 `go test`，直接跑测试二进制

`go test` 除了 vet 之外，还要额外走一遍依赖图解析 + 链接 + 临时目录管理。在本机
这套流程本身就不稳定（同一命令可能 5 秒完成，也可能几分钟无输出）。更可靠的做法是
**把测试编译成二进制，然后自己执行**：

```bash
# 一次性编译（正常时段约 14 秒；机器变慢时可能几十分钟，见第二节）
# CWD 必须在包目录里，否则相对路径 fixture 会失败
cd server
go test -vet=off -c -o /d/GC3/server.test.exe ./server/

# 反复运行，改数据库/改环境变量都不用重编译
ARTEX_PG_DSN="postgres://artex:pw@127.0.0.1:5432/artex_test?sslmode=disable" \
  /d/GC3/server.test.exe -test.timeout 40m -test.v
```

**CWD 陷阱**：`server/skills_builtin_test.go` 用 `filepath.Join("..", "skills")` 定位
skill 目录，`go test` 会把 CWD 设成包目录，所以能过；但如果直接跑二进制而 CWD 是仓库
根，`..` 就指到了仓库外面，10 个 skill 相关测试会**假失败**（报
`skills: The system cannot find the file specified`）。跑之前务必 `cd server`。

## 二之三、给 `server` 包测试准备隔离数据库

`server` 包的 `TestMain` 会用 `db.DSN()` 连库并抢 advisory lock（7337741002），
配置来源优先级是 `ARTEX_PG_DSN` > `config.json`。**仓库里没有 `config.json`**，
所以不设环境变量时 `db.DSN()` 直接报错，`TestMain` 跳过抢锁，所有带 `t.Skip` 守卫的
数据库测试全部静默跳过 —— 实测有 6 个 SKIP 就是这么来的。

这会掩盖真实缺陷：`server/skills_injection_test.go` 的
`TestSkillVisibilityBindsPortedSkills` 从落地起就一直被跳过，导致「新部署不给
worker/pentest 绑定方法论 skill」的缺陷长期没人发现。

**必须用独立库，绝不能指向 `artex_audit`**：测试里有跨表 `DELETE` 清理，跑一次就会
清掉生产数据。

本机 PostgreSQL 不在 `C:\Program Files` 下，客户端在：

```
D:\PenTesting\Tools\db-connect\postgresql-server\bin\psql.exe
```

建库：

```bash
export PGPASSWORD=01EDTUB7HLyFQ3ii
PSQL="D:/PenTesting/Tools/db-connect/postgresql-server/bin/psql.exe"
"$PSQL" -h 127.0.0.1 -U artex -d postgres \
  -c "DROP DATABASE IF EXISTS artex_test WITH (FORCE);" \
  -c "CREATE DATABASE artex_test;"
```

> 本机 5432 上还跑着一个 Acunetix 自带的 `postgres.exe`，它**不监听**端口。
> 真正在监听的是 PID 6384（`D:\PenTesting\Tools\db-connect\...`），别搞混。

## 二之四、`schema.sql` 每次启动都全量执行，里面有会改数据的迁移语句

`db.Open` 会 `//go:embed` 后把整个 `schema.sql` 执行一遍（幂等设计）。但其中
`ALTER TABLE intercept_pending ...` 之后跟着两条**无条件 UPDATE**：

```sql
UPDATE intercept_pending SET decision_source='manual'
 WHERE decision_source <> 'manual'
   AND (audit->>'decision_reason' LIKE '人工允许%' OR ... LIKE '人工拒绝%');
```

后果：任何一次重新 `db.Open`，都会把历史行按 `decision_reason` 文案重刷一遍
`decision_source`。这会让「先跑模型决策、再跑人工决策」这类**跨用例的状态依赖**
出现串味 —— 单独跑 `TestCaptureApprovalLifecycle/model_deny` 是绿的，和
`human_deny` 一起跑就红。

这不是产品 bug（生产库里 `decision_source` 全是 `model`，符合预期），而是
**测试自身对环境复用的假设过强**。`agent` 包的 `TestCaptureApprovalLifecycle`
目前稳定失败（4 个子用例里 3 个），经改动前后对照确认属于 upstream 遗留问题
（`87b3c3c` 引入，长期因未设 DSN 而跳过），与 skill 可见性无关，不要误判成本轮回归。

## 二之五、`intercept` 包在 Windows 上必然失败（平台限制，不是缺陷）

`go test ./intercept/` 会有 8 个用例红，特征是：

```
--- FAIL: TestStaticSedSnapshotsMatchNativeSed/s/a.b/MATCH/
    static_sed_test.go:26: snapshot differs from sed: ... ReadError:命令内脚本写入内容或执行路径不确定
--- FAIL: TestInlineShellCaptureCombinations/sequential_loops
    scripts_test.go:80: status="incomplete" want="not_applicable" ... ReadError:Shell 内联执行内容不确定
```

**原因**：这几个测试验证的是「静态分析推导出的脚本文本 == 真实 shell 执行结果」，
基准值靠 `exec.Command("sed", program, path).Output()` 获取，被测命令串里还有
`bash new.sh`。**Windows 既没有原生 `sed` 也没有 `bash`**，基准取不到，全红属预期。

`ScriptCaptureStatus:incomplete` / `Shell 内联执行内容不确定` 来自
`intercept/scripts.go:274`，是静态分析器**主动声明「这里推不出来」的合法分支**，
不是崩溃或 panic。

这些测试文件来自上游 merge（`bffa2b5` 等），`intercept/` 最近提交也都是上游整合
（`880de9e` merge RuoJi6/ARTEX v0.3.27）。**在 WSL / Linux / macOS 上跑才有效**，
Windows 下不要把它们的失败当成回归。

## 三、`go version` 与 `VERSION` 文件不一致（已知，暂未处理）

- `go version` 报 `go1.26.10`
- `C:\Program Files\Go\VERSION` 文件内容为 `go1.26.1`
- `go.mod` 要求 `go 1.26.10`

这会让 go 在构建时转发到 toolchain 版本
（`C:\Users\1\go\pkg\mod\golang.org\toolchain@v0.0.1-go1.26.10.windows-amd64\bin\go.exe`），
进程列表里会同时出现两个 `go.exe`。**这是正常的 toolchain 转发机制，不是死锁**，无需处理。

补充两条踩坑经验：

- 这个转发机制曾被误判为「`go build` 卡死的原因」，已排除 —— 直接用
  `toolchain@.../bin/go.exe` 单跑，卡死现象一模一样。
- 想临时绕开转发可直接用该路径的二进制，但记得同时设 `GOTOOLCHAIN=local`，
  否则它还会再往上一级找。注意系统自带的 1.26.1 **不能满足** `go.mod` 的
  `go 1.26.10` 要求，硬用 `GOTOOLCHAIN=local` 会报
  `go.mod requires go >= 1.26.10 (running go 1.26.1)`。
- 本机自带 Go 是 1.26.1、实际工具链是 1.26.10，两者混用时**别忘了一次性对齐**，
  比如临时把测试模块的 `go.mod` 写成 `go 1.26.1` 就能用系统 Go 快速验证环境，
  不必等 toolchain 转发。

## 四、磁盘

- C 盘长期接近满（约 7G 可用），Next dev 写 `.next` 缓存时容易报
  `TurbopackInternalError: failed to write ... error 112`（磁盘空间不足）。
  遇到前端全页面 500 白屏先查这里，不是代码问题。
- 项目迁移副本放在 `D:\WorkBuddy\artex-ld`，D 盘空间充裕（约 99G 可用）。
- `.next` 用 junction 指向别的盘**不可行**：Turbopack 会从缓存目录向上找
  `node_modules`，跨盘链接会破坏模块解析，报 `Cannot find module 'react/jsx-runtime'`。
  要么整个项目一起搬，要么别动缓存目录。

## 五、报告相关依赖

- docx 导出依赖 `python3` + `python-docx`。缺失时接口会**明确返回 501** 并提示，
  不会等到后台任务失败才抛 Python traceback（该守卫见 `server/report.go` 的 `docxReady`）。
- 没有 docx 能力时，Markdown 导出是唯一可用格式（纯 Go 实现，无 Python 依赖）。
