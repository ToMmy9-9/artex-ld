# 本机开发环境注意事项

记录在当前这台 Windows 开发机上实测到的环境坑，避免后来者重复踩。

## 一、跑 Go 测试必须加 `-vet=off`

**现象**：`go test ./xxx/` 看起来像"编译卡死"——几分钟没有任何输出，进程 CPU 接近 0，
也不派生子进程。很容易误判为磁盘满、缓存损坏或工具链故障。

**真实原因**：`go test` 默认会先执行 `go vet` 做静态检查，而 `go vet` 在这台机器上
会卡住不再推进。

**对照数据**（`reportx` 包，同一份代码、同一个 GOCACHE）：

| 命令 | 耗时 |
|---|---|
| `go build ./reportx/`（热缓存） | **3.3 秒** |
| `go test ./reportx/ -vet=off` | **0.061 秒，全绿** |
| `go test ./reportx/`（默认带 vet） | 8 分钟超时未完成 |
| `go vet ./reportx/`（单独执行） | 2 分钟无输出、卡死 |

**结论**：

```bash
# 一律这样跑
go test ./reportx/ -count=1 -vet=off
go test ./db/ -count=1 -vet=off
ARTEX_PG_DSN="postgres://..." go test ./server/ -p 1 -count=1 -vet=off
```

不加 `-vet=off` 会白等数小时。想单独做静态检查时，请换一台机器或等 `go vet`
问题修好后再跑。

## 二、GOCACHE 用 `D:\GoCache2`，不要用 `D:\GoCache`

`D:\GoCache`（约 9.3G）里的条目已经失效，命中它时构建会异常慢。
`D:\GoCache2` 是后来重建的干净缓存，工作正常。

```bash
GOCACHE="D:/GoCache2" go build ./cmd/artex
```

注意 Go 的缓存 key 包含源码绝对路径，所以**同一个包在不同目录下编译不会互相命中**。
在 C 盘仓库和 D 盘迁移副本之间切换时，第一次编译都要重新建缓存（`server` 这类大包
首次约需 30 分钟以上），之后才会快。

## 三、`go version` 与 `VERSION` 文件不一致（已知，暂未处理）

- `go version` 报 `go1.26.10`
- `C:\Program Files\Go\VERSION` 文件内容为 `go1.26.1`
- `go.mod` 要求 `go 1.26.10`

这会让 go 在构建时转发到 toolchain 版本
（`C:\Users\1\go\pkg\mod\golang.org\toolchain@v0.0.1-go1.26.10.windows-amd64\bin\go.exe`），
进程列表里会同时出现两个 `go.exe`。**这是正常的 toolchain 转发机制，不是死锁**，
无需处理。

## 四、磁盘

- C 盘长期接近满（约 7G 可用），Next dev 写 `.next` 缓存时容易报
  `TurbopackInternalError: failed to write ... error 112`（磁盘空间不足）。
  遇到前端全页面 500 白屏先查这里，不是代码问题。
- 项目迁移副本放在 `D:\WorkBuddy\artex-ld`，D 盘空间充裕（约 99G 可用）。
- `.next` 用 junction 指向别的盘**不可行**：Turbopack 会从缓存目录向上找
  `node_modules`，跨盘链接会破坏模块解析，报 `Cannot find module 'react/jsx-runtime'`。
  要么整个项目一起搬，要么别动缓存目录。

## 五、报告相关依赖

- docx 导出依赖 `python3` + `python-docx`。缺失时接口会**明确返回 501** 并提示，
  不会等到后台任务失败才抛 Python traceback（该守卫见 `server/report.go` 的 `docxReady`）。
- 没有 docx 能力时，Markdown 导出是唯一可用格式（纯 Go 实现，无 Python 依赖）。
