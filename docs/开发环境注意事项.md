# 本机开发环境注意事项

记录在当前这台 Windows 开发机上实测到的环境坑，避免后来者重复踩。

## 一、跑 Go 测试必须加 `-vet=off`

**现象**：`go test ./xxx/` 看起来像"编译卡死"——几分钟没有任何输出，进程 CPU 接近 0，
也不派生子进程。很容易误判为磁盘满、缓存损坏或工具链故障。

**真实原因**：`go test` 默认会先执行 `go vet` 做静态检查，而 `go vet` 在这台机器上
会卡住不再推进。

**对照数据**（`reportx` 包，同一份代码、同一个 GOCACHE）：

| 命令 | 耗时 |
|---|---|
| `go build ./reportx/`（热缓存） | **3.3 秒** |
| `go test ./reportx/ -vet=off` | **0.061 秒，全绿** |
| `go test ./reportx/`（默认带 vet） | 8 分钟超时未完成 |
| `go vet ./reportx/`（单独执行） | 2 分钟无输出、卡死 |

**结论**：

```bash
# 一律这样跑
go test ./reportx/ -count=1 -vet=off
go test ./db/ -count=1 -vet=off
ARTEX_PG_DSN="postgres://..." go test ./server/ -p 1 -count=1 -vet=off
```

不加 `-vet=off` 会白等数小时。想单独做静态检查时，请换一台机器或等 `go vet`
问题修好后再跑。

## 二、GOCACHE 用 `D:\GoCache2`，不要用 `D:\GoCache`

`D:\GoCache`（约 9.3G）里的条目已经失效，命中它时构建会异常慢。
`D:\GoCache2` 是后来重建的干净缓存，工作正常。

```bash
GOCACHE="D:/GoCache2" go build ./cmd/artex
```

**实测对照**（同一个 hello-world，同一个 go 版本）：

| GOCACHE | 耗时 |
|---|---|
| 全新空目录 | **5 秒** |
| 小缓存目录 | 13 秒 |
| `D:\GoCache`（9.3G / 22863 文件） | 超过 8 分钟未完成，被 SIGTERM |

具体退化点不在文件体积，而在 **NTFS 目录项查找**：对该目录里任意一个小文件做
`stat` 要 **116 毫秒**（正常应 < 1ms）。编译一个中等包要查上千个缓存条目，
累计就是几十分钟。目录被反复增删后容易出现这种状态，把整个目录删掉重建即可。

注意 Go 的缓存 key 包含源码绝对路径，所以**同一个包在不同目录下编译不会互相命中**。
在 C 盘仓库和 D 盘迁移副本之间切换时，第一次编译都要重新建缓存（`server` 这类大包
首次约需 30 分钟以上），之后才会快。

## 二之二、跑大包测试别用 `go test`，直接跑测试二进制

`go test` 除了 vet 之外，还要额外走一遍依赖图解析 + 链接 + 临时目录管理。在本机
这套流程本身就不稳定（同一命令可能 5 秒完成，也可能几分钟无输出）。更可靠的做法是
**把测试编译成二进制，然后自己执行**：

```bash
# 一次性编译（14 秒），CWD 必须在包目录里，否则相对路径 fixture 会失败
cd server
go test -vet=off -c -o /d/Temp/server.test.exe ./server/

# 反复运行，改数据库/改环境变量都不用重编译
ARTEX_PG_DSN="postgres://artex:pw@127.0.0.1:5432/artex_test?sslmode=disable" \
  /d/Temp/server.test.exe -test.timeout 40m -test.v
```

**CWD 陷阱**：`server/skills_builtin_test.go` 用 `filepath.Join("..", "skills")` 定位
skill 目录，`go test` 会把 CWD 设成包目录，所以能过；但如果直接跑二进制而 CWD 是仓库
根，`..` 就指到了仓库外面，10 个 skill 相关测试会**假失败**（报
`skills: The system cannot find the file specified`）。跑之前务必 `cd server`。

## 二之三、给 `server` 包测试准备隔离数据库

`server` 包的 `TestMain` 会用 `db.DSN()` 连库并抢 advisory lock（7337741002），
配置来源优先级是 `ARTEX_PG_DSN` > `config.json`。**仓库里没有 `config.json`**，
所以不设环境变量时 `db.DSN()` 直接报错，`TestMain` 跳过抢锁，所有带 `t.Skip` 守卫的
数据库测试全部静默跳过 —— 实测有 6 个 SKIP 就是这么来的。

这会掩盖真实缺陷：`server/skills_injection_test.go` 的
`TestSkillVisibilityBindsPortedSkills` 从落地起就一直被跳过，导致「新部署不给
worker/pentest 绑定方法论 skill」的缺陷长期没人发现。

**必须用独立库，绝不能指向 `artex_audit`**：测试里有跨表 `DELETE` 清理，跑一次就会
清掉生产数据。

本机 PostgreSQL 不在 `C:\Program Files` 下，客户端在：

```
D:\PenTesting\Tools\db-connect\postgresql-server\bin\psql.exe
```

建库：

```bash
export PGPASSWORD=01EDTUB7HLyFQ3ii
PSQL="D:/PenTesting/Tools/db-connect/postgresql-server/bin/psql.exe"
"$PSQL" -h 127.0.0.1 -U artex -d postgres \
  -c "DROP DATABASE IF EXISTS artex_test WITH (FORCE);" \
  -c "CREATE DATABASE artex_test;"
```

> 本机 5432 上还跑着一个 Acunetix 自带的 `postgres.exe`，它**不监听**端口。
> 真正在监听的是 PID 6384（`D:\PenTesting\Tools\db-connect\...`），别搞混。

## 二之四、`schema.sql` 每次启动都全量执行，里面有会改数据的迁移语句

`db.Open` 会 `//go:embed` 后把整个 `schema.sql` 执行一遍（幂等设计）。但其中
`ALTER TABLE intercept_pending ...` 之后跟着两条**无条件 UPDATE**：

```sql
UPDATE intercept_pending SET decision_source='manual'
 WHERE decision_source <> 'manual'
   AND (audit->>'decision_reason' LIKE '人工允许%' OR ... LIKE '人工拒绝%');
```

后果：任何一次重新 `db.Open`，都会把历史行按 `decision_reason` 文案重刷一遍
`decision_source`。这会让「先跑模型决策、再跑人工决策」这类**跨用例的状态依赖**
出现串味 —— 单独跑 `TestCaptureApprovalLifecycle/model_deny` 是绿的，和
`human_deny` 一起跑就红。

这不是产品 bug（生产库里 `decision_source` 全是 `model`，符合预期），而是
**测试自身对环境复用的假设过强**。`agent` 包的 `TestCaptureApprovalLifecycle`
目前稳定失败（4 个子用例里 3 个），经改动前后对照确认属于 upstream 遗留问题
（`87b3c3c` 引入，长期因未设 DSN 而跳过），与 skill 可见性无关，不要误判成本轮回归。

## 三、`go version` 与 `VERSION` 文件不一致（已知，暂未处理）

- `go version` 报 `go1.26.10`
- `C:\Program Files\Go\VERSION` 文件内容为 `go1.26.1`
- `go.mod` 要求 `go 1.26.10`

这会让 go 在构建时转发到 toolchain 版本
（`C:\Users\1\go\pkg\mod\golang.org\toolchain@v0.0.1-go1.26.10.windows-amd64\bin\go.exe`），
进程列表里会同时出现两个 `go.exe`。**这是正常的 toolchain 转发机制，不是死锁**，
无需处理。

## 四、磁盘

- C 盘长期接近满（约 7G 可用），Next dev 写 `.next` 缓存时容易报
  `TurbopackInternalError: failed to write ... error 112`（磁盘空间不足）。
  遇到前端全页面 500 白屏先查这里，不是代码问题。
- 项目迁移副本放在 `D:\WorkBuddy\artex-ld`，D 盘空间充裕（约 99G 可用）。
- `.next` 用 junction 指向别的盘**不可行**：Turbopack 会从缓存目录向上找
  `node_modules`，跨盘链接会破坏模块解析，报 `Cannot find module 'react/jsx-runtime'`。
  要么整个项目一起搬，要么别动缓存目录。

## 五、报告相关依赖

- docx 导出依赖 `python3` + `python-docx`。缺失时接口会**明确返回 501** 并提示，
  不会等到后台任务失败才抛 Python traceback（该守卫见 `server/report.go` 的 `docxReady`）。
- 没有 docx 能力时，Markdown 导出是唯一可用格式（纯 Go 实现，无 Python 依赖）。
